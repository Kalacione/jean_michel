## 2. Diagnostic croisé — constats utilisateur ↔ preuves dans la conversation

### 2.1 Hang 10h sans message d'erreur ni timeout
- **Preuve** : gap entre `042639321_web-search-specialist_tool_response.md` (04:26:39) et `110843163_web-search-specialist_thought.md` (11:08:43) = **6h42 sans aucun artefact**. La conversation a été lancée à 04:08 ; le dev l'a retrouvée figée plus tard.
- **Sortie post-hang** (`110843187_web-search-specialist_response.md`) : contient un `<thought ...` littéral non parsé → la couche LLM/Ollama a retourné une réponse mal formée que rien n'a détecté.
- **Code à interroger** : aucun timeout par appel LLM dans `OllamaClient`. Aucune limite "wall-clock" par requête dans `orchestrator._run_request`. Le `MAX_STEPS_PER_REQUEST = 15` (mentionné README) est un compteur d'itérations, pas un mur temporel.
- **Constat dev** : "limite de temps par action d'agent, un truc réglable dans la config, 2 minutes par défaut" → à implémenter dans le client LLM + au niveau de l'orchestrateur (wall-clock par tool_call + par requête).

### 2.2 `plan.md` pas mis à jour
- **Preuve** : 5 invocations distinctes du planner sur la conversation. Sur les 5 :
  - **Phase 1** (040922) : `workspace_create_file('plan.md')` OK.
  - **Phase 3** (041314 et 041429) : planner retourne le plan **en texte inline**, **aucun `workspace_create_file` ni `workspace_str_replace`** (cf. `040929360`, `041314646`, `041429252` — kind `response`).
  - **Phase 6** (042126) : `workspace_str_replace('plan.md', ...)` OK.
  - **Phase 6 bis** (042220) : `workspace_create_file('workspace/plan.md')` → **nested**.
- **Aucune** des invocations ne met à jour le plan **avec les findings** des agents en aval. Le planner ré-écrit toujours le squelette macro, jamais les résultats nichés.
- Le paradigme/output contract du planner ne mentionne pas l'obligation d'incorporer les rendus de recherche.

### 2.3 Recréation d'un sous-dossier `workspace/` dans `workspace/`
- **Preuve directe** : artefact `042220949_planner_tool_call.md` : `workspace_create_file(path='workspace/plan.md')`. Conséquence : `workspace/workspace/plan.md` créé.
- Confirmé par `042503101_wikipedia-specialist_tool_response.md` qui montre **deux fichiers `plan.md`** dans le workspace.
- Cause probable : le prompt du planner injecte le chemin `workspace/plan.md` (préfixe inclus) — le LLM le recopie tel quel dans l'argument `path`, alors que `workspace_create_file` attend un path **relatif à workspace** (donc juste `plan.md`).

### 2.4 `{"error": "File already exists: plan.md. DO NOT call workspace_create_file again..."}`
- **Preuve directe** : artefact `042100211_planner_tool_response.md`. Cette erreur survient **alors que** le prompt système du planner (042029288) contient explicitement le protocole "create OR str_replace".
- Le mécanisme d'injection du contenu existant du workspace dans le prompt (mentionné par le dev) **n'a pas empêché** l'agent de re-tenter `workspace_create_file`. Soit l'injection ne contient pas la liste des fichiers existants, soit le LLM ignore l'info parce qu'elle n'est pas saillante.

### 2.5 Plan évasif, pas mis à jour avec les préconisations
- **Preuve** : `workspace/plan.md` final reste générique : 6 catégories de domaines, statuts ⬜ pending. Aucun ajout après les 3 web-search + 2 wikipedia (qui ont collectivement exécuté ~50 queries).
- Aucun artefact `_briefing.md` de jean-michel vers le planner ne contient un résumé des findings à intégrer. Le planner n'est sollicité que pour (re-)produire le plan macro.

### 2.6 Profondeur jamais > 1 malgré l'approfondissement
- **Preuve** : aucune `_prompt.md` ne porte `depth: 2` ou plus dans toute la conversation. Aucun specialist n'appelle `delegate_to` (sauf l'abus de wikipedia-specialist en phase 4 → tentative `delegate_to(planner)` qui n'aboutit même pas).
- Conséquences :
  - **`signal_convergence` n'est jamais offert** aux specialists (paradigme convergence_gate actif uniquement à depth ≥ 2).
  - **`critical-thinker` n'est jamais invoqué** → pipeline GATHER→CRITIQUE→BUILD cassé.
  - **`document-builder` n'est jamais invoqué** → aucun fichier final produit.

### 2.7 Paradigme erroné dans le planner ("Now I must call return_to_user")
- **Preuve** : les 3 `_response.md` du planner (040929360, 041314646, 041429252, 042133930, 042229561) sont tous des `return_to_user(answer='plan.md written/updated.')`. Conforme au prompt courant mais en contradiction logique avec le rôle attendu (un planner devrait signaler à l'orchestrateur, pas "répondre à l'utilisateur").
- Le rôle DB du planner est probablement `specialist` ou `router` ; le contrat de sortie injecté lui permet donc `return_to_user`. À corriger : soit le planner devient un rôle dédié, soit son prompt restreint explicitement.

### 2.8 Plan ne contient pas l'imbrication des recherches
- **Preuve** : le `plan.md` (workspace/plan.md final, 2348 bytes) n'a aucune sous-section par query. La table "Status" mappe 1:1 step→agent→deliverable sans détail des sous-recherches.

### 2.9 Aucun fichier de résultat produit dans workspace
- **Preuve quantitative** : sur les 3 runs web-search-specialist + 2 runs wikipedia-specialist (combinant ~75 appels d'outils de recherche), **0 appel à `workspace_create_file`** (ni à un quelconque outil d'écriture).
- **Cause structurelle** : web-search-specialist et wikipedia-specialist **n'ont pas le grant `agent_workspace_grants`** dans la BDD (sinon ils l'auraient utilisé). Les briefings de jean-michel leur demandent pourtant explicitement de produire des fichiers (`expected=markdown file` dans `040953533` et suivants).
- **Mismatch contractuel** : jean-michel envoie des briefings qui supposent une capacité que les specialists n'ont pas. Aucune validation côté orchestrateur.
- Les `_tool_response.md` produits restent **uniquement** dans le journal d'artefacts, jamais référencés ni indexés.

### 2.10 Erreurs `file not found` non remontées
- Aucune erreur `file not found` explicite trouvée dans cette conversation. Mais le pattern voisin (lecture de `workspace/plan.md` au mauvais chemin) est traité silencieusement.
- Constat dev valide : il faut un **fail-fast** côté orchestrateur sur erreurs filesystem critiques (file not found, path traversal denied, quota dépassé).

## 3. Pathologies systémiques transversales

1. **Boucles de raisonnement non détectées intra-agent**
   Le LLM oublie ses propres tool_calls précédents au tour suivant. Le filtre `Duplicate call detected` de l'orchestrateur n'arrête pas la boucle, il la déplace : l'agent reformule à un caractère près (`dumps` → `dump`). Phase 5 = 7 queries arXiv distinctes. Phase 7 = 10 `wikipedia_search('MediaWiki API')` consécutifs.

2. **Aucun mécanisme de "rate-limit sémantique"**
   Pas de hash sémantique des queries. Pas de "tu as déjà cherché X, voici les résultats — ne recommence pas". Une mémoire courte du specialist (résumé des N derniers tool_responses ré-injectée dans le contexte) serait probablement décisive.

3. **Step budget = filet trop tardif**
   `MAX_STEPS_PER_REQUEST = 15` se déclenche après que l'agent a brûlé 15 cycles inutiles. Aucune détection préventive ("3 queries quasi-identiques d'affilée → stop").

4. **Aucune validation post-délégation**
   Quand un specialist retourne `step_budget_exhausted`, jean-michel ne déclenche aucune action de récupération. Il ré-essaie avec un autre agent ou redélègue au planner. Aucun artefact "post-mortem" n'est créé.

5. **Mismatch grants ↔ briefings**
   Jean-michel envoie des `expected=markdown file` à des agents sans grant d'écriture. Le pipeline `research_phase_routing` (GATHER → CRITIQUE → BUILD) devrait imposer le passage par `document-builder` à la fin. Ici, jean-michel **saute systématiquement** cette étape.

6. **`delegate_to` jamais utilisé entre specialists**
   Le pipeline théorique exige web-search/wikipedia → critical-thinker → document-builder. Mais aucun specialist ne délègue à un autre. Soit jean-michel doit chaîner explicitement, soit les specialists doivent avoir le droit de chaîner — actuellement ni l'un ni l'autre.

7. **Aucun wall-clock**
   Ollama peut hanguer sur un prompt long. Aucun timeout configuré dans `OllamaClient` ni au niveau de l'orchestrateur. Conséquence : la conversation peut occuper la VRAM indéfiniment.

8. **Planner sans cycle de vie**
   Le planner est appelé 5 fois sur cette conversation sans aucune contrainte d'idempotence. L'orchestrateur ne détecte pas "tu as déjà un plan, n'en redemande pas un, mets-le à jour".

9. **Path injection naïve**
   Le path `workspace/plan.md` du briefing est recopié verbatim par le LLM dans l'argument `path` du tool. L'outil `workspace_create_file` devrait soit normaliser (strip `workspace/` préfixe), soit refuser un chemin contenant `workspace/`.

10. **Output validation absente**
    L'artefact `110843187_web-search-specialist_response.md` contient un `<thought ...` littéral. Rien ne valide que le payload d'un `return_to_user` ou `signal_convergence` est sémantiquement cohérent.

## 4. Pistes (à débattre, pas à implémenter au pas de course)

- **Wall-clock par appel LLM** dans `OllamaClient` + **wall-clock par requête** dans `orchestrator._run_request`. Config dans `config.py` (`LLM_CALL_TIMEOUT_SECONDS=120`, `REQUEST_WALL_CLOCK_SECONDS=600`).
- **Mémoire courte intra-specialist** : injecter dans le prompt à chaque tour un récapitulatif des `(query, top_url)` déjà obtenus.
- **Détection de boucle sémantique** : `Counter` des queries normalisées (lower-cased, sans ponctuation, n-grams) sur les K dernières — au-delà d'un seuil, l'orchestrateur force `return_to_user`.
- **Workspace path normalization** : `workspace_create_file` strip `^workspace/` du `path` arg ; refuse `..`, refuse path absolu — déjà fait pour les deux derniers mais pas pour le préfixe.
- **Lock du planner** : au plus une invocation `delegate_to(planner)` par requête. Au-delà, l'orchestrateur force l'utilisation de `workspace_str_replace` côté jean-michel.
- **Pipeline GATHER→CRITIQUE→BUILD imposé** : si jean-michel a délégué à un research specialist, il **doit** ensuite déléguer à critical-thinker puis document-builder avant de pouvoir `return_to_user`. À vérifier dans le paradigme `research_phase_routing`.
- **Validation du payload `return_to_user`** : refuser une string qui contient `<thought` ou `<|...|>` ou autre marqueur tokenisation Gemma — le marker indique un parsing raté.
- **Re-design du contrat du planner** : sortie obligatoirement = soit `workspace_create_file('plan.md')` soit `workspace_str_replace('plan.md', ...)`. Pas d'autre tool. Pas de `return_to_user`. Possibilité d'ajouter un nouveau "control verb" `planner_done` pour rendre la main à l'orchestrateur.
- **Promotion à depth ≥ 2** : revoir pourquoi web-search/wikipedia ne délèguent jamais — soit le grant `delegate_to` est absent, soit le prompt ne les y incite pas.
